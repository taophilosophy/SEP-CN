# 翻译工程标准 v1.0（SEP-CN 流程规范）

**版本**：v1.0（2026-10-27）。本标准把术语库、翻译、审阅、校对流程整合为可执行规范，取代本文档此前的论述式版本。与 `specs/001-sep-sync-pipeline`（管线规格）、`specs/002-term-consistency`（术语一致性规格）引用对齐、互不覆盖：管线、抓取与目录同步事宜以规格为准，术语与文稿质量的操作性规程以本标准为准。修订规则见 S10。

## S1 双表架构

| 文件 | 角色 | 写入时机 |
| ---- | ---- | ---- |
| `yi-zhe-shuo-ming.md` | 登记簿：全库术语裁定单一事实源（原文、译法、首现、裁定日期） | 翻译遇到新术语，先登记后使用 |
| `qian-yan/ci-hui-biao.md` | 发布表：面向读者的三列对照表（英语、中文、备注） | 任务收尾时从登记簿合并；修正须有据 |

发布表质量模型四维度，全部可用工具判定：**真实性**（译法有据，备注记来源）、**有效性**（键值映射无歧义，冲突须有裁定理由）、**可追溯性**（备注可回溯来源或裁定提交，对齐 FR-017）、**同步性**（双表定期双向同步）。

## S2 术语生命周期：四个回路

```text
①登记    遇新词 → 查双表 → 无则登记 yi-zhe-shuo-ming.md → 再进正文
②发布    任务收尾 → 登记簿新行合并进 ci-hui-biao.md → 过 glossary_lint
③回收    git 提交信息/旧译文挖掘 → 裁定增补 → tasks/ci-hui-biao.json 待办清零
④复核    lint 0 问题 + 联网抽查 → 逐条修正 → 报告留痕（fang-fa-lun/）
```

候选批量进入②前走**分档裁定**：**A 档**（教科书级标准术语）凭通行译法直裁；**B 档**（存疑）联网核查后裁，来源写入备注；**C 档**（无通行译名或泛词）挂起（held:理由）或驳回（rejected:理由），记入 `tasks/term-candidates.json` 的 status 字段。裁定产出 manifest（逐条人工给出译法，清单即裁定记录），**入库于 `tasks/manifests/<日期>-batch<N>.json`**，经 `script/publish_terms.py` 按折叠键定位插入双表——登记簿空格风格、发布表紧凑风格，脚本只做机械定位；发布后必跑 glossary_lint。2026-10-27 三批共 65 条经此通道发布（37+23+5），发布表至 659 行。

## S3 三审三校质量门（对齐 FR-012）

六道顺序：一校 → 二校 → 三校 → 初审 → 复审 → 终审。每道必须有**可判定输出**，不接受口头完成：

| 道 | 重点 | 可判定输出 |
| ---- | ---- | ---- |
| 一校（准确性） | 漏译、错译、事实错误 | 对照 en/ 原文逐节核销记录；按[正反误用手册](zheng-fan-wu-yong-shou-ce.md)第一节排查日常词误译 |
| 二校（语言） | 欧化句、口吻、流畅 | 逐条修改清单（改前改后，禁止机械批量） |
| 三校（体例） | 引号、空格、术语、格式 | 检查脚本 0 问题；正文用词与登记簿一致（grep 校验） |
| 初审（自审签字） | 对照原文整体自审 | 执行者＋时间戳写入任务 JSON |
| 复审（逐句回核） | 原文与逻辑一致性 | 按正反误用手册第二节核查语境分流取词；问题单 |
| 终审（终稿验收） | CI 全绿 | CI 状态链接；任务状态置 done |

更新任务只对变更段落重走相应校次（不复查旧错原则）；**术语性修改必须回写登记簿**——术语是全库资产。复核结论必须由工具验证，不得以"报告已写"代替执行（2026-10-27 教训：Argument/Aspect 两行报告在而执行漏，被 v2 抓出）。

## S4 任务文件规范（tasks/*.json）

任务记录沿用 `tasks/a/alcmaeon.json` 奠定的模式，统一字段：

```json
{
  "slug": "任务标识（词条 slug 或主题名如 ci-hui-biao）",
  "kind": "retranslate | update | glossary-maintenance | …",
  "zh_doc": "对应的中文 md 路径",
  "state": "当前状态（自定枚举，须在 steps 中可追溯）",
  "steps": [{"step": "节点名", "status": "ok|fail", "actor": "执行者", "at": "ISO 时间", "evidence": "可复核凭证：哈希/锚点/diff/脚本输出"}],
  "todo": [{"item": "待办", "status": "pending", "subtasks": [{"item": "…", "status": "pending"}]}],
  "blockers": [],
  "created_at": "ISO 时间",
  "version_pin": {"pubinfo_date": "…", "archive_edition": "…", "sha256": "…"}
}
```

规则：每个 step 必须带 evidence（FR-017）；version_pin 仅词条任务必填；todo 随执行推进，清零后任务方可置 done。

## S5 缺陷分类与处置

| 类 | 定义 | 处置 |
| ---- | ---- | ---- |
| A 事实性 | 人名、年代、版本、指称对象错误 | 联网核查后改，登记簿同步 |
| B 术语性 | 译名误用、正反误用、键值冲突 | 逐条修正＋lint 规则化 |
| C 语言性 | 欧化、生硬、语法 | 二校逐条清单 |
| D 格式性 | 坏行、重复、标点、异体字 | lint 捕获，修复后 0 问题验收 |

原则：**一次性缺陷逐条修，重复性缺陷工具化**——同类问题出现两次以上，必须沉淀为 lint 规则或手册条目。

## S6 别名与重名处置（去重合并规则 v3）

三层折叠检测：**fold**（NFC＋去附加符号＋撇号归一＋去符号）→ **fold2**（其上再归一属格残留 's、英式/美式拼写、-isation 类后缀）。检查四类：

* **同指异名**（拼写变体、缩写、跨语同义、单复数、属格）→ 白名单放行，备注交叉指引；
* **同键多指**（如两名 Ammonius）→ 分行并列，备注注明各自所指；
* **同姓异人** → 裸姓氏行必须带消歧备注（观照名单见 glossary_lint.py 的 HOMONYM_NOTE_REQUIRED，含 benjamin）；
* **术语别名** → 备注记“又称”。

v3 新增三查（首跑 22 条，精化后全部处置）：

1. **强折叠近重复**：fold2 相同的行对——同译名提示合并或入 FOLD2_SAME_OK，异译名须裁定；fold1 层已裁定者（FOLD_DUP_OK、SAME_KEY_MULTI_SENSE_OK）不重复上报。
2. **词序倒置**：词多重集相同、顺序不同且折叠键不同才报（同键重复不在此列）。
3. **词缀包含一致性**：token 序列包含的行对（全名/姓氏、单复数），被包含键须 ≥2 词（排除 Theory/Truth 类单 token 泛词误报），译名按斜杠分项后互不为子串且双方无消歧备注才报；命中处置为**消歧备注**（重名）或**语境分流注**（连续统/连续体、同一论/同一性），不做机械合并——译名合并永远由人逐条裁定。

## S7 质量门命令

```sh
# 一键全量质量门（词汇表 lint + mu-lu-s 检测 + tasks/*.json 合法性 + markdownlint）
python script/check_all.py

# 单项
python script/glossary_lint.py        # 词汇表结构与键归一门禁（白名单外 0 问题为绿）
python tools/check_terms.py           # 术语一致性门禁（CI 已接入，他会话维护）
python script/check_mulu_s.py         # mu-lu-s 对应性（只检测不改动）
python script/extract_terms.py        # 术语候选提取（语料扩充后重跑）
```

**双门禁分工**（两门都过才算术语层全绿）：`tools/check_terms.py`（specs/002，CI 侧）做译法**集合**比对——登记簿与发布表译法集合互斥为硬错误、真子集为滞后告警，另查登记册自洽（废弃行、裁定日期、同键重复）；`script/glossary_lint.py`（本标准，写作侧）做英文键**归一**与结构检查——变音/强折叠、坏行、重名消歧、词序倒置、词缀包含、表格边界。登记簿人名表现为 4 列（原文、译法、备注、裁定日期），与术语表对齐。

markdownlint 以仓库根 `.markdownlint-cli2.jsonc` 为准（CI 同源），不再传 `--config .github/.markdownlint.json`；表格一律紧凑风格（单元格内侧不加空格，MD060）。check_all 对 `mu-lu-s.md`（用户裁定只检测不改动）、`specs/**`（他会话产物）、`guan-yu/**` 与 `pending/**`（既有页面历史格式违规/WIP，待归属会话以 `script/fix_table_style.py` 机械修复）与 `.github/sep-sync-report/**`（管线自动生成物）予以豁免，其余文件非 0 即阻断。工具批量修复前必须先在单个文件上验证 diff——2026-10-27 曾因正则吞换行把 guan-yu 三页的多行表格拼成一行，已回滚（S3 教训同样适用于工具变更）。

## S8 提交与会话纪律

* 提交前先 `git log` / `git status` 核对 HEAD——并行会话会插入提交、可能卷走工作区改动；提交失败（no changes added）重新 add + commit 即可。
* 小步高频提交：一个单元完成立即提交；只 add 与本次工作相关的文件。
* 一律 `git commit --no-gpg-sign`；未经用户要求不 push、不 force。
* 提交信息格式：`范围：动作与要点`（中文一行，如"词汇表复核收尾：从提交信息增补 5 条裁定并登记 9 条新裁定"）。
* 他人会话产物（specs/、baseline/、tools/、yuanwen/ 的管线部分、mu-lu-s.md）不改动；发现其缺陷以报告或任务文件留痕，不越权修复。

## S9 度量

* **登记簿覆盖率**：行数随任务增长，每完成一个词条任务应有新增行。
* **lint 门**：glossary_lint 问题数非 0 即阻断提交。
* **正反误用捕获率**：复审阶段新发现 B 类缺陷应趋近 0；连续捕获即回填手册。
* **回收债**：tasks/ci-hui-biao.json 中 pending 子任务数，随回路 ③ 递减。
