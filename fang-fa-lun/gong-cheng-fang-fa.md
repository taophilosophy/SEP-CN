# 翻译工程方法：术语库、流程与质量门

本文是 `specs/001-sep-sync-pipeline`（管线规格）的工程方法论补充：把术语库、翻译流程、审阅流程、校对流程当作一个软件工程系统来设计，明确每个环节的输入、输出、质量门与缺陷处置路径。术语登记的宪法依据见 `yi-zhe-shuo-ming.md` 卷首说明（新术语先登记、后使用）。

## 一、双表架构与词汇表质量模型

项目有两个术语文件，角色不同，禁止混用：

| 文件 | 角色 | 写入时机 |
| ---- | ---- | ---- |
| `yi-zhe-shuo-ming.md` | 登记簿：全库术语裁定单一事实源，逐词条登记（原文、译法、首现、裁定日期） | 翻译中遇到新术语，先登记后使用 |
| `qian-yan/ci-hui-biao.md` | 发布表：面向读者的三列对照表（英语、中文、备注） | 任务收尾时从登记簿批量合并；修正须有据 |

发布表的质量模型有四个维度，全部可用工具判定：

1. **真实性**：每条译法所指为真、有据可查（备注列记录来源：出版中译本、权威词典、学术论文）。复核手段：联网核查＋回到原始 PDF／SEP 原文。
2. **有效性**：英文键与中文值映射无歧义——无坏行、无完全重复、同键异译与中文碰撞必须有裁定理由。
3. **可追溯性**：备注可回溯到具体来源或裁定提交（FR-017 的术语版实现）。
4. **同步性**：登记簿与发布表定期双向同步，防止漂移（见第三节回路 ③）。

## 二、术语数据流：四个回路

```text
①登记    翻译遇到新词 → 查发布表/登记簿 → 无则登记 yi-zhe-shuo-ming.md → 再进正文
②发布    任务收尾 → 登记簿新行批量合并进 ci-hui-biao.md → 跑 glossary_lint.py
③回收    git 提交信息/旧译文挖掘 → 裁定短语增补 → tasks/ci-hui-biao.json 待办清零
④复核    lint 0 问题 + 联网抽查 → 修正 → 报告留痕（fang-fa-lun/）
```

* 回路 ③ 已验证有效：2026-10-27 遍历全部 3184 条提交信息，从 6 条裁定短语提交中增补 5 条缺失术语（Chancellor 总务长、Philip the Chancellor 总务长菲利普、Constitution 构成、Nominalism 唯名论、anomalous monism 变异一元论）。方法与清单见 `tasks/ci-hui-biao.json`。
* 回路 ④ 的首次全量复核见 [词汇表复核报告](ci-hui-biao-fu-he-bao-gao.md)：46 处修正、24 项联网核查、两处“维持原状”裁定同样留痕。

## 三、三审三校的质量门设计（对齐 FR-012）

六道顺序：一校 → 二校 → 三校 → 初审 → 复审 → 终审。每道必须有**可判定的输出**，不接受“已读过”式的口头完成：

| 道 | 重点 | 可判定输出 |
| ---- | ---- | ---- |
| 一校（准确性） | 漏译、错译、事实错误 | 对照 en/ 原文逐节核销记录；按[正反误用手册](zheng-fan-wu-yong-shou-ce.md)第一节排查日常词误译 |
| 二校（语言） | 欧化句、口吻、流畅 | 修改清单（逐条列出改前改后，禁止机械批量） |
| 三校（体例） | 引号、空格、术语、格式 | 引号/加粗检查脚本 0 问题；markdownlint 0 问题；正文用词与登记簿一致（grep 校验） |
| 初审（自审签字） | 对照原文整体自审 | 执行者＋时间戳写入任务 JSON |
| 复审（逐句回核） | 原文与逻辑一致性 | 按正反误用手册第二节核查语境分流取词；问题单 |
| 终审（终稿验收） | CI 全绿 | CI 状态链接；任务状态置 done |

更新任务（上游词条修订）只对变更段落重走相应校次（不复查旧错原则），但**术语性修改必须回写登记簿**——术语是全库资产，不是单篇内部事务。

## 四、缺陷分类学与处置路径

| 类 | 定义 | 本轮复核占比 | 处置 |
| ---- | ---- | ---- | ---- |
| A 事实性 | 人名、年代、版本、指称对象错误 | 约 1/4 | 联网核查三次后改，登记簿同步 |
| B 术语性 | 译名误用、正反误用、键值冲突 | 约 1/2 | 逐条修正＋lint 规则化（能写成检查就写成检查） |
| C 语言性 | 欧化、生硬、语法 | 翻译期主责 | 二校逐条清单 |
| D 格式性 | 坏行、重复、标点、异体字 | 约 1/4 | lint 自动捕获，修复后 0 问题验收 |

原则：**一次性缺陷逐条修，重复性缺陷工具化**。凡同类问题出现两次以上，必须沉淀为 lint 规则或手册条目，而不是指望下一次人工小心。

## 五、工具与质量门清单

```sh
# 词汇表有效性检查（白名单外 0 问题为绿）
python script/glossary_lint.py

# 目录对应性检测（mu-lu-s.md 只检测不改动）
python script/check_mulu_s.py

# markdownlint（发布表与新文档必过）
markdownlint-cli2 "**/*.md" "!en/**" "!node_modules/**" "!script/**" --config .github/.markdownlint.json
```

提交纪律：提交前先 `git log`/`git status` 核对 HEAD（并行会话会插入提交）；小步高频提交；`git commit --no-gpg-sign`；提交信息用中文一行简述。

## 六、度量

* **术语覆盖率**：登记簿行数随任务增长曲线（期望：每完成一个词条任务都有新增行）。
* **lint 缺陷密度**：每次提交后 glossary_lint 问题数应为 0；非 0 即阻断合并。
* **正反误用捕获率**：一校按手册排查后，复审阶段新发现的 B 类缺陷数应趋近 0——若复审连续捕获，说明手册缺条目，回填之。
* **回收债**：tasks/ci-hui-biao.json 中 pending 子任务数，随回路 ③ 执行递减。
