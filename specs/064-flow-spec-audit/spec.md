### 0.2 目标

以全要素为论域（节点／状态／判据／工具／规则／文档／标准／阶段／战役／标记），完成四件事：

1. **全量审计**：每族实读基数、覆盖关系、缺口，逐项附证据。
2. **形式化核验**：把 063 的 AX1–AX14 作为候选结构约束，扩展 AX15–AX30；逐条区分定义、机检不变量、条件定理、经验假设与人审事项。只有构造出满足全部前提的模型才 claim 一致性；只有分别验证其余公理成立的反例才支持独立性。已知反例与被证伪命题须如实保留。
3. **标准化**：要素族 × 适用标准（ISO／GB／CY/T）映射，标出符合／部分／偏离／不适用与缺口。
4. **规范化与格式化**：编号、命名、字段、引用、文档形态、JSON schema、文件命名全部收敛为可机检规则。

### 0.3 非目标

1. **本轮不实施**：只修订文档、撤销不成立结论并给出建议。此前经单独批准形成的 rules/11 与 habermas 机器扫描作为历史证据保留，不构成继续执行的授权。
2. 不改 `en/`、`yuanwen/`、`SUMMARY.md`、译文、任务 JSON 与登记册数据。
3. 不重写历史 ADR（现 90 份）；格式规范只约束新件，历史头通过解析器兼容。
4. 不删除任何节点／阶段号（裁定 A：22 节点全部保留）。
5. 不新建与 `pipeline.json` 重复的节点级三件套（§6.4 判据）。

### 0.4 验收判据

1. 要素基数全部实读可复算；规则域与文档实体、当前与目标分别计数。
2. 审计结论每条有事实源位置；缺口区分阻断、高、中、低及已关闭项。
3. 形式化：AX1–AX30 与 CT1–CT17 逐项标明“定义／候选／条件成立／被证伪／人审”；不得再要求“全部可判定”或把反例动机写成独立性证明。
4. 标准化：每族至少一个适用标准或“不适用”理由；跨领域类比不得写成标准直接要求。
5. 规范化与格式化：拟机检项须有明确谓词、输入、预期命中量级和承载体；人审项不得伪装成结构谓词。
6. 案 B 已于 2026-11-26 裁定 A（不实施，保留 22 节点）；如重提，须先消除 P12／段尾闭合冲突并重走裁定，未消除前不得进入实施。

### 2.5 标准审计（96 条登记 vs 节点锚点）

- **规范层级**：标准身份、版本、采纳状态与承接的单一事实源是 `rules/standards.json`；条款落点细则是 `rules/10`。specs/061 §5 是 2026-11-25 的**评估时矩阵与证据**，不是实时权威；063 阶段表引用标准应以“标准键＋`rules/10` 条款锚点”表达，不复制整段版本结论（G5 重新定性为“展示性复制”，不是事实双源）。
- `cited` 层＝引用事实与落点；`adopted` 层＝采纳—承接—工具三元组；二者由 `standards_table.py` 派生 README，不在 064 另建标准册。
- **版本复核（2026-11-26）**：29148:2018 现行并于 2024 复审确认（DIS 在研）；15289:2019 于 2025 确认、2026-06-11 转 90.92 修订；26514:2022 已发布现行。故“三项均待核”不成立；待办只是把新证据回写机器登记册，属另一实施动作。G11 由“版本待核”改为“证据已核、登记回写待办”。
- **ISO/IEC 25010:2023** 为第 2 版、**九特性**、适用于 ICT／软件产品质量；它不是翻译质量模型。可候选用于工具产品质量或作为**类比分类**，但不得把“功能适合性”直接等同译文准确性，也不得据此声称译文符合 25010（G12 降为可选项）。

### 12.2 结论（先说判断）

96 个工具有 95 个已评级（另 1 个 `__init__` 为包标记），全表见 `results/toolchain-rust-audit.md`：**A 级 26（25 A＋1 A+）／B 级 29／C 级 30／D 级 10／包标记 1＝96**。rev 10 补评 `campaign`、`summary_sync` 为 C，删除重复的 `en_integrity` 行。

- **D 级 10 项禁迁**：转换器（`yuanwen`／`parser`，受 I2/I3 锁定）、一次性迁移／清史脚本、浏览器自动化等。

### 12.3 三条前置事实改变了“全量迁移”的必要性

1. **依赖并非全为零**：AST 实读 96 件中 95 件未直接导入非标准库；`tl_crawler.py` 直接依赖 `cryptography` 与 `playwright`。故“依赖安全”不能作为全仓迁移论据，也不能再写“零第三方依赖”。
2. **正则语义风险是最大单点**：`re` 被 62 个工具使用，含反向引用、lookaround、条件组；Rust `regex` 不支持回溯与反向引用。直译可能静默改变语义，故正则审计是前置门，不可等价改写者留 Python。
3. **行为锁定与证据**：21 项门禁＋55 个测试文件锁定的是**已被测到的行为**，不是全部语义。迁移需输入快照、规范化差分、性质／边界测试与人工抽核；黄金测试是必要证据之一，不是“唯一安全网”。

**正则语义审计（B4/B5 前置，不可跳过）**：逐工具列出不可直译模式（反向引用、lookaround、条件组），给出改写方案与等价性测试；无等价改写者降 C 留 Python。全表见 `results/toolchain-rust-audit.md` §10。

### 12.6 黄金主测试

每个迁移候选先录制 `tools/golden/<tool>/`：最小但真实的输入快照＋原始 stdout／stderr＋退出码＋产物哈希＋平台与工具版本。比对规则按输出契约分三档：①声明为 byte-contract 的产物逐字节；②JSON 经显式 schema 规范化后比结构值与告警集合；③含时间戳、绝对路径、临时目录的字段须在录制 schema 中声明为动态字段并做替换，禁止笼统“逐字节”或“全排序”。同一输入须覆盖退出码 0／1／2 与边界样本。

### 12.7 Python 现代化（受控变更，不是“零风险”）

现无 `pyproject.toml`／无统一类型检查／无格式化器／无 Python 锁文件。候选顺序：

| 项 | 内容 | 风险控制 |
| ---- | ---- | ---- |
| 依赖与元数据 | `pyproject.toml`，区分运行时／开发／可选（`cryptography`、`playwright`） | 先锁现有解释器与行为；不以新依赖改写代码 |
| 格式化与 lint | 先 `ruff check` 基线报告，再按目录小批格式化 | 不做全库一次性 reformat；不夹带语义改动 |
| 类型检查 | `mypy` 从库模块起步，逐模块收紧 | 每模块有测试与回退；不以 `# type: ignore` 刷绿 |
| 运行器／锁 | `uv` 先在 CI 影子作业验证，再切换 | 保留 Python 直跑回退；双机与 CI 解释器同版 |

收益与风险均须用基线测试、启动时间和 CI 稳定性衡量；不预设“1/20 成本换 60–70% 收益”这类未经测量的比例。

## 13 语言选型偏好与其他语言评估

### 13.1 语言选型偏好规则（软件工程理论，2026-11-26 用户批准）

**规则定位**：本条把 §12 的逐工具评级与 §13.2 的语言评估收敛为**可执行的选型序**，适用于今后新增与既有工具的语言决策。它是用户批准的工程偏好，不是“已证明唯一最优”的数学结论；改变分工须走 ADR。

| 规则 | 名称 | 内容 | 落地 |
| ---- | ---- | ---- | ---- |
| **LPR-1** | 调用寿命分档 | “长期稳定调用”须四问全满足：①高频（门禁／CI／批量作业每次必调）；②契约稳定（输入可快照、输出可差分）；③长期维护（预期跨季度）；④关键路径（失败即阻断提交或产出）。任一不满足即归“其余档” | 评级表 A／B／C／D 的分档复核 |
| **LPR-2** | 长期档优先 Rust | 长期档**优先 Rust**：tokio multi-thread 承担 I/O 并发、rayon 承担 CPU 并行；有界并发与背压；`#![forbid(unsafe_code)]`、edition 2024、单二进制；每项须交“并发设计说明”（线程模型、并行粒度、上界、背压、失败语义、结果确定性）；不可并行段须显式论证（全局序或单资源约束），不得默认单线程 | §12.4；T040–T042、T050–T093 |
| **LPR-3** | 其余档用 Python | 其余档**默认 Python 3.15**；受 I2／I3 字节锁定、Playwright 生态、`re` 回溯／反向引用语义约束者**必须**留 Python | §12.2 C／D 级；T030–T034 |
| **LPR-4** | 其他语言再评估 | **Go 已裁定不引入**；**C#／.NET 与 Zig 经用户裁定（2026-11-26）不采用、无需核验**；Bun 工具链升级另案。今后引入任何新语言须过六项硬门——构建可复现、语义等价可证、生态覆盖（如浏览器自动化）、平台支持、供应链安全、维护成本可承担——并经 ADR 才可改变分工 | §13.2；ADR（实施时取号） |
| **LPR-5** | 演进式落地 | 本规则**不授权任何即时迁移**；既有工具随 064 的具体语言重构任务（S4–S9，T040–T093）逐个落地、演进；每项仍须过黄金／差分／性质测试与正则语义审计前置门（§12.5–§12.6），并单独立项取得批准 | tasks.md S4–S9；plan §7 WP-R1 |

**与评级表的映射**：A 级 26 项＝长期档候选（LPR-2，仍须逐项过证据门）；B 级 29 项**默认留 Python**，迁 Rust 须先证明四问全满足并单独论证；C 级 30 项、D 级 10 项＝其余档（LPR-3；D 级禁迁）。

**与三门定案的关系**：本规则是“Rust＋Python 3.15＋Bun、不引入 Go”的选型细则，不推翻三门边界，只规定两档组件在各门内的归属顺序。

**四条反例（防止规则被滥用）**：

1. 不得以“Rust 更快”跳过 LPR-1 四问——一次性迁移、低频运维、生成器不因性能偏好改语言。
2. 不得为并发而并发：抓取并发受站点速率与退避约束（ADR-0069），并发数不是 KPI，更不得以“多线程”为由绕过限速。
3. 不得把 D 级转换器（`yuanwen`／`parser`）当作“长期高频”迁走——它们受 I2／I3 逐字节锁定，属 LPR-3 的强制留 Python 项。
4. 不得用“其他语言也在评估”拖延既定迁移，也不得未经 ADR 引入第四门语言。

### 13.2 其他语言评估表（版本滚动核实）

| 语言 | 版本（核实） | 并发／安全 | 文本/正则生态 | 部署 | 结论 |
| ---- | ---- | ---- | ---- | ---- | ---- |
| **Rust** | 1.100／e2024 | tokio＋rayon，真并行；禁 unsafe 可达 | regex＝RE2，**无回溯/反向引用** | 单二进制 | **核心层首选** |
| **Go** | 1.27.4 | goroutine，最简；GC＋静态类型 | RE2 同族（**同限制**） | 单二进制 | 已裁定不引入：单语言性价比高，但第二门系统语言成本大于收益 |
| **Python** | 3.15.2 | asyncio／threading（GIL）；动态＋mypy | `re` 最全（回溯/反向引用）、unicodedata 最强 | 解释器 | 边缘/生成器/转换器（**必须保留**） |
| TypeScript／Bun | 本机 1.4.5（2026-11-19） | 事件循环；类型层 | 弱（数值/正则） | bun 运行时 | 站点维持既有；工具链升级另案 |
| C#／.NET | — | async/await；GC＋静态 | Regex 支持回溯／反向引用 | AOT 单文件 | **不采用**（用户 2026-11-26 裁定；无需核验） |
| Zig | — | 手动；手动 | 弱 | 单二进制 | **不采用**（用户 2026-11-26 裁定；无需核验） |

**反直觉但重要的一点**：若把“正则语义零漂移”放在第一权重，最平滑的目标其实是 **.NET**（其 Regex 支持回溯与反向引用），而 Rust 与 Go 同属 RE2 族、都受限。这意味着 Rust/Go 迁移的 B4/B5 批必须付出正则改写成本——这是评估里最容易被忽略的隐性代价，已在 §12.5 设为独立前置门。该分析仅作方法论记录：C#／.NET 与 Zig 已由用户裁定不采用，无需核验。

### 13.3 定案与分工理由

**定案（2026-11-26 用户批准）**：**三门**——Rust（候选内核与并发抓取）＋Python 3.15（转换器、爬虫、一次性、生成器、测试网）＋Bun（站点）。这是决策边界，不是“已证明唯一最优”的数学结论；两档组件的归属按 §13.1 的 LPR-1–5 判定。

**为什么不加 Go**：Go 在单语言覆盖并发与部署上有优势，但本仓已保留 Python 与 Bun；再引入第三门系统语言会新增构建、CI、并发模型与错误处理面的维护成本。该判断是工程取舍，尚无以工时和缺陷率为数据源的量化评估。

**语言分工理由（可复核）**：Rust 的候选价值在 CPU／内存安全与可控并发；Python 的保留理由是 I2 字节锁定、Playwright 生态与低改动摩擦；Bun 的保留理由是站点既有。不得写成“唯一不可替代／交集为空”的绝对命题；若未来出现等价载体，应按 ADR 重评。

### 15.2 字段（schema `sep-registry/v1`，15 个已定义字段／12 个无条件必填＋1 个条件必填）

| 字段 | 类型 | 必填 | 说明 | 标准依据 |

### 15.3 生命周期枚举

| 值 | 语义 | 默认 TTL | 到期动作 |
| ---- | ---- | ---- | ---- |
| `permanent` | 与仓库同寿（长期表默认） | 永不 | 不删；sha 不符＝红 |
| `epoch` | 纪元期（本轮重译纪元内有效，如 results 快照） | 纪元收口 | `archive` |
| `campaign` | 战役期（战役收口后归档） | 战役收口 | `archive` |
| `session` | 会话期（调试输出、临时下载） | 逐条显式给出，无隐式默认 | 默认只标 `expired`；删除须显式 `--go` 与复核 |
| `one-shot` | 一次性脚本产物 | 逐条显式给出 | 默认归档或保留；不得仅因到期自动删除 |

### 15.4 状态与清理动作矩阵

状态判定：`active`（文件在且 sha 符合）｜`expired`（`now − modified_at > ttl_days`；`now` 须固定或显式注入，`verified_at` 只记校验时点、不延长 TTL）｜`orphaned`（登记了但文件不存在）｜`superseded`（同 path 有新 active 条目，旧条目留史）｜`pruned`（条目已清退，仅 temp 保留历史）。

> **悬空字段订正（rev 12）**：原写 `last_used_at`，但 15 字段中没有该字段，属不可求值判据。现改用 `modified_at`（最近一次写入）；若将来需要“仅校验也续期”，必须显式新增字段并升 schema 版本，不得在判据里引用未定义字段。

**path 唯一性只约束 active**：历史 `superseded`／`pruned` 可保留同 path 的旧条目，否则状态机自相矛盾。`id` 全局唯一且不复用。

| 状态 × 策略 | `protect` | `expire` | `archive` |
| ---- | ---- | ---- | ---- |
| `active` | 保留 | 保留至 TTL | 保留 |
| `expired` | **告警**（违背生命周期） | 默认只标候选；`--go` 且二次确认后删除，置 `pruned` | 移入 `archive/`＋置 `superseded` |
| `orphaned` | **红**（长期物丢失） | 只删条目，不据此推断可删除其他文件 | 只删条目 |
| `superseded` | 保留（历史） | 保留历史；若需清文件须另列清单 | 保留 |

### 15.5 单一事实源约束（关键）

| ---- | ---- | ---- |
| `en/` 逐文件 sha | `baseline/entries.json`（1873 条） | **不登记**；long 表只登记目录级条目指向该事实源 |
| `baseline/en-patches` | `INDEX.json` | 不逐条登记 |
| `tasks/` | 任务 JSON 自身 | 不登记 |
| `baseline/registry-long.json` 自身 | 版本控制＋提交哈希 | **不自引用**：表内 sha 无法证明含自身当前字节的完整性；完整性由提交／tag 与外部校验值承担 |

**sha 校验频率分层**（避免 1873 级全量散列拖慢 CI）：

| 场景 | 范围 |
| ---- | ---- |
| 每次 CI／提交前 | 仅本次变更路径＋`git_tracked=false` 条目 |
| 每周／每月 | long 表全量（目录级条目展开后校验） |
| 每次 `clean --check` | temp 表全量（本机量小） |

### 15.7 与既有机制的关系

- 与 `clean.py`（ADR-0003）：clean 负责“未跟踪垃圾”的发现与删除；登记表负责“已跟踪或已命名产物”的保留／过期判定。互补不重叠。
- 与 `check_junk.py`：junk 管根目录白名单（空间维度）；登记表管产物生命周期（时间维度）。
- 与 `check_doc_size.py`：`size_bytes` 字段是“大体积产物”判定依据。
- 与 ADR-0081/0082 清史纪律：长期表是“未来留存”的落地形态——凡 `permanent` 产物，其存在与 sha 受门禁保护，与记录管理偏离（D4）的补救方向一致。
