## 3 设计原则

1. **证据先于迁移**：先有行为契约与基线，再决定是否换语言。
2. **契约优先于实现**：CLI 输出、退出码、动态字段、产物哈希先写清；Python 与 Rust 都服从同一契约。
3. **单源优先**：节点／判据取 `pipeline.json`；标准取 `standards.json`＋`rules/10`；标识取 `naming.json`；不在 064 建平行账。
4. **局部可逆**：一项工具、一个门禁、一张表各自可回退；不做全库格式化或大爆炸式切换。
5. **上位约束优先**：案 B、阶段轨、文档形态均不得违反 P1–P33；局部计数定理不能覆盖 P12。
6. **语言选型有序**：长期稳定调用（LPR-1 四问全满足）优先 Rust，且须多并发多线程；其余默认 Python；其他语言过六项硬门并经 ADR 才可改变分工（spec §13.1）。

## 6 黄金／差分测试

```
tools/golden/<tool>/
├─ input/                   # 最小可复现输入；裁剪须保持判定不变
├─ expected/
│  ├─ stdout.raw            # 仅对声明 byte-contract 的输出
│  ├─ result.json           # 结构化结果（规范化 schema）
│  └─ artifacts.sha256      # 不可变产物
└─ meta.json                # commit、工具版本、平台、录制时点、动态字段声明
```

- 比对优先级：契约字段等值 → 告警／问题集合等值 → 不可变产物哈希等值 → 原始字节（仅声明者）。
- JSON 键序、浮点格式、路径分隔符、时间戳按 `meta.json` 显式规范化；不得笼统“全排序”或“全逐字节”。
- 必须覆盖 0／1／2 退出码与至少一个 Unicode、一个空输入、一个边界样本。
- 黄金样本只证明覆盖内等价；还须性质测试、差分模糊测试与人工抽核。CT16 的“无黄金不可证”已撤销。
