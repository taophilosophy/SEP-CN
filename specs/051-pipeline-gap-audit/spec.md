# 翻译全流程遗漏审计（2026-11-19）

**性质**：只读审计 + 已落地修复记录｜**边界**：不改译文、不改 `en/`、不启新翻译
**触发**：用户「反思翻译全流程是否有其他遗漏」
**方法**：不凭流程文档推断，一律对本仓真实数据求值（journal 1,197 条、tasks 1,200 条、SUMMARY 1,872 条、译文 1,872 文件、判据 19 项）。

## 0. 结论摘要

审计出 **7 处已修**、**7 处待决策**。最严重的一条不在"判据不够严"，而在**判据可以悬空登记而全绿**：`errata_check`、`markdownlint`、`ci_all` 三个判据名长期没有可解析的承载体，`check_stages` 只查"登记双向一致"，于是形式全绿掩盖了"这三条判据从未真正执行"。第二严重的是**进度分母口径**：五项进度读数以 journal 1,197 件为分母，而 SUMMARY 声明 1,872 件，675 件从不出现在任何一行。

## 1. 已修（本轮）

### 1.1 判据承载体可解析（S5）

`check_stages` 原四谓词只查"每个判据至多一个硬拦节点"与"登记表双向一致"，**不查判据有没有实现**。实测三项无同名 `tools/*.py`：

| 判据 | 真实承载体 | 处置 |
| ---- | ---- | ---- |
| `errata_check` | `check_pairs.py` 的 `errata-apply` 轴 | `criteria_carrier` kind=axis |
| `markdownlint` | `format.yml`（bunx）+ `.markdownlint-cli2.jsonc` | kind=external，level=warn |
| `ci_all` | `check_all.py` 聚合 + `checks.yml` | kind=aggregate |

新增 S5 两谓词：**①判据承载体可解析**（axis 须宿主内真含该规则名）、**②硬拦判据不得由告警级承载**。三组负向样本各自触发、基线全绿；配套 3 项负向单测（判据总数 11 → 13）。

### 1.2 markdownlint 的"声明硬拦、实际不拦"

pipeline 原把 `markdownlint` 列入 S3 的 `criteria` 且 `S3.gate_owner=true`，即**声明为硬拦**。实测：CI 里 `format.yml` 为 `continue-on-error: true`（告警级，rules/05 亦如此记载），`tools/` 无同名工具，`task_ops` 不调用。三者一致表明它从来不拦任何东西。

处置：从 S3 `criteria` 移入 `criteria_advisory`，`criteria_carrier` 记 `level=warn`，注释保留裁定依据（ADR-0061）。**不是降级判据，是让声明追上事实。**

### 1.3 进度分母口径（675 件账外）

`progress.py` 五项读数（完成／强制集／饱和／在途／未开工）的分母是 `journal` 词条 **1,197**，而 SUMMARY 声明正式词条 **1,872**。差额 675 件既无任务也无 journal，此前不出现在任何一行——读 `PROGRESS.md` 的人会把"未开工 766"当成全库未开工量。

实测二维账（1,872 = 1,440 骨架 + 432 有正文）：

| 内容状态 | 账内（有 journal） | 账外（无 journal） |
| ---- | ---- | ---- |
| 仅标题骨架 | 765 | 675 |
| 有正文 | 432 | 0 |

已显式化：新增"账外词条""骨架合计""有正文"三行 + 分母口径注；`count_skeletons()` 纯函数带 4 项单测（含"骨架 ≠ 别名/占位母行"与二维和恒等）。

### 1.4 账实不符无判据（19 件）

`task_ops.clear()` 的语义是"写入 H1、置 cleared"，所以 `cleared` 的唯一合法含义是**正文已置空**。实测 **18 件 state=cleared 却有正文**（357–37,018 汉字），且 journal 无任何 `pass` 事件：

| 来源 | 证据 |
| ---- | ---- |
| 跨机 WIP 收编 | 2026-11-13 提交「在途账本 WIP 快照（接手 S 批前收编）」把工作区 1,127 文件入库；`axiom-choice.md` 在该提交 +505 行，而其 clear 发生在 11-12 18:39、`task_ops` 记录状态仍 cleared |
| 时间线钉死 | 该件 11-12 18:46 版本 = 2 行（合法清空态），11-13 05:40 版本 = 507 行（写回） |

危害：`check_pairs --gate` 是**状态感知**的（仅 ≥s2.4 硬拦），cleared 不在 `GATE_STATES` 内 → 这 18 件的内容**逃过全部体例门禁**；同时它们不被任何批次选中（状态调度按 state 挑目标），成为"既在库里、又不在账上"的内容。

新增 `tools/check_taskfile_invariant.py`：I1 清账不变量（cleared ⟹ 仅 H1）、I2 过程记录不变量（有正文 ⟹ journal 至少一个 pass），默认告警档、`--strict` 升硬，7 项单测；已接入 `PROGRESS.md` 的「账实不符」行，使每次生成都能看见。

### 1.5 逐段对齐只覆盖 16 件（用户指令是"禁止抽查"）

`para_align.py` 的条目表是**硬编码 16 件**（specs/007 一次性清单）。2026-10-29 用户指令是"全部译文逐段与 html 直接比较，禁止抽查"——实际覆盖 16/432。且该脚本无论传什么参数都跑全清单并 `w` 覆盖全量凭证（本轮实测一次误跑即抹账，已 `git checkout` 复原）。

两处处置：① `para_align.py` 加 argv 子集 + 非全量写 `-partial` 文件（主凭证仅全量可写）；② 新增 `bin/para_align_full.py`，对全库 432 件有正文者跑同一套 `en_blocks/zh_blocks/align`，只读、另落账。

**同型缺陷在新工具上复现一次**：`para_align_full.py` 初版同样无条件写主凭证，本审计中一次 `--limit 1` 试跑把 432 件账抹成 1 件（已 `git checkout` 复原）。修法同款——局部运行（`--limit`/`--slugs`）只写 `-partial`。记此一笔，因为"凭证可被单次试跑覆盖"是**判官自身的可靠性缺陷**，与它判什么无关。

**全库首跑校正链**（这条是审计方法的核心发现）：

| 口径 | 未配对 | 未配对率 | 件数 |
| ---- | ---- | ---- | ---- |
| 朴素 1:1 贪心对齐（原算法） | 20,743 / 77,585 | 26.7% | 308 |
| ＋脚注键存在即不计（译文侧有该键） | 756 | 0.97% | 34 |
| ＋脚注键名规范化（内容特征词可见即算搬运） | **420** | **0.54%** | **9** |

26.7% 里 96% 是**对齐器假阳性**：`align()` 是同序 1:1 贪心，脚注定义区只要有一处增删（译注、条序、合并）就整体错位，后续块全部推成"未配对"。真实缺口 9 件，其中 2 件是实质截断：

| 件 | EN 块未配对 | 译文汉字 | 镜像字节 | 判定 |
| ---- | ---- | ---- | ---- | ---- |
| `haecceitism` | 199 / 249 | 2,895 | 96,897 | 正文截断（属 §1.4 的 18 件） |
| `hamann` | 195 / 263 | 357 | 82,729 | 正文仅存导言 9 行（同属 18 件） |
| 其余 7 件 | 1–12 | — | — | 脚注/致谢/外部链接等尾节差异，量级 ≤12 块 |

**结论**：`hamann`／`haecceitism` 的截断正是"跨机 WIP 收编 + 状态未同步"的直接后果——它们既被计为"未开工"，又已带内容上站。

## 4. 与既有规格的关系

- 不取代 `specs/044`（B0/B1 基线）与 `specs/045`（并行性）：本审计判的是**流程账实与判据承载体**，与"源格式一致""并发安全"是不同面。
- `specs/036`（源审计存量补课）待批状态未变；本审计为它补了"为什么必须批"的量化依据（400 件强制集零覆盖）。
- `specs/039`（md 标准化）的脚注键名规范化口径，是本审计排除 96% 假阳性的依据，二者一致。
