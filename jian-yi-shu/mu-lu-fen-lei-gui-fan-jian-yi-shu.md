## 一、方向声明（rules/08 §1）

* **意图复述**：用户要求给出目录分类存储的最佳优化建议，并提供可依据的国标／ISO／IEEE 规范与开源实践；用户判断现有目录定义结构不清晰、存在大量未定义情况。
* **目标**：①用可复算数据核验"未定义"的规模与位置；②给出有版本钉的规范依据；③给出可判定、可回退的分阶段方案。
* **非目标**：不改任何规则、门禁、目录与文件位置；不新增根级条目；不重排词条层；不提交任何实施改动。
* **验收判据**：本建议书每条诊断附可复算命令；每条建议附判据、成本与回退；规范条目附版本状态与核验日期。
* **作废条件**：若实测发现"未定义"规模低于本书记录的一个数量级，或规范版本状态与本书记录不符，则相应章节作废重做。
* **适用规范基线**：见 §四（本次新查证 12 项，核验日期 2026-11-17）。

### 2.1 未在 `rules/01` 目录职责表定义的 18 项

其中两项值得单独指出：

## 三、诊断：三个机制，不是十八处疏漏

**D1 双轨清单无派生关系。** 存在性由 `ROOT_ALLOW` 管，职责由 `rules/01` 表管，两者无生成关系。改一处不动另一处，差异即累积。当前差集 18 项。

**D2 四轴混切产生多解。** 现有归置同时用四个维度判定落点：①文件用途（脚本／凭证／文档）②入库状态（跟踪／忽略）③生命周期（临时／受控／永久）④所属工程（`specs/NNN`）。四轴交叉时，同一文件常有 2–3 个"都说得通"的位置（`specs/001` 的 JSON 即 ①③④ 冲突的产物）。

**D3 容器无 schema。** 一级目录有职责表，二级容器（`specs/<NNN>/`、`baseline/`、`tasks/`）没有。41 个规格目录长出 8 种子目录名，`execution-log` 分裂为文件与目录两形态，无人能凭规则判断"我该建 `bin/` 还是把脚本放根 `script/`"。

一句话：**词条层定义得很严（`SUMMARY.md` ＋ `check_summary` 锁死），治理与工程层几乎没有容器定义。** 用户"大量未定义"的判断成立，但重心不在根目录散件，而在二级容器。

## 四、规范与实践（版本钉，核验 2026-11-17）

| 需求 | 规范／实践 | 状态 | 可借用的是什么 |
| --- | --- | --- | --- |
| 分类方案、记录控制 | **ISO 15489-1:2016** | 现行；**2026-11-06 进入 90.92 拟修订**，目标 2029-07 | 以业务职能（function/activity）而非组织形式分类；分类方案与保留处置同属 records controls |
| 同上，中文采标 | **GB/T 26162-2021** | 现行（2022-07-01 实施） | 等同采用 ISO 15489-1:2016；**代替 GB/T 26162.1-2010（已废止 2022-07-01）** |
| 记录元数据 | **ISO 23081-1:2017** | 现行（2023-05-25 确认） | 元数据四维：业务、法规、责任、技术 |
| 元数据中文 | **GB/T 26163.1-2010** | 现行，**修订中**（计划号 20252306-T-469）；GB/T 26163.2-2023 现行 | 元数据元素定义框架 |
| 配置项、基线、配置库 | **IEEE 828-2012** | **Inactive-Reserved**（2023-03-30 停维护）；修订 PAR P828 活跃（2021-02-10 批准） | 配置项识别、变更控制、状态报告、构建与发布；配置库分层 |
| 架构描述 | **ISO/IEC/IEEE 42010:2022** | 现行（2022-11-07，Ed.2，62 页） | 关注点分离、viewpoint／view、跨视图一致性（correspondence） |
| 信息项 | **ISO/IEC/IEEE 15289:2019** | 现行（项目已登记） | 标识／版本／状态／责任者／保留 五属性 |
| 文件整理（件、分类、档号） | **DA/T 22-2015** | 现行（2016-06-01 实施，代替 2000 版） | "以件为单位"、组件／分类／排列／编号／编目 五步 |
| 电子文件归档 | **GB/T 18894-2016** | 现行（2023-12-28 复审"继续有效"） | 归档范围、元数据、存储结构 |
| 软件文档编制 | **GB/T 8567-2006** | 现行（2022-01-10 复审"继续有效"） | 文档分类与内容要求 |
| 文档四分类 | **Diátaxis**（diataxis.fr） | 无版本号，持续维护 | tutorial／how-to／reference／explanation；**按用户需求分类，不按文件类型分类** |
| 文件级许可声明 | **REUSE 3.3**（2024-11-14） | 现行，工具 6.2.0（2025-10-27） | 每文件 SPDX 头 ＋ 根 `LICENSES/`；不可注释文件用 `.license` 边车 |

### 4.1 三点判断

1. **没有一份标准直接规定"代码仓库目录怎么排"。** ISO 15489／GB/T 26162 管"记录的分类与保留"，IEEE 828 管"配置项与基线"，42010 管"架构描述的关注点分离"，DA/T 22 管"件的整理与档号"。仓库布局要从这四者**组合推导**，不能直接套用。声称"某标准规定目录结构"的说法都不可信。
2. **最贴近本问题的两份是 IEEE 828 与 ISO 15489。** 前者给出"受控库／基线／配置项"的三分，后者给出"按职能分类＋保留处置"的方法。二者组合恰好覆盖本仓库的痛点。
3. **版本风险要登记。** ISO 15489-1 在核验前 11 天刚进入修订轨道（目标 2029），GB/T 26163.1 修订计划在批。若引用条款号，须以现行版为准并在修订发布后重核——这与项目"版本钉"纪律同构。

## 五、目标模型：三元组 ＋ 七问

### 5.1 三元组（任一文件由三个坐标唯一确定）

| 坐标 | 取值 | 判据 |
| --- | --- | --- |
| **域** | `product` 产品／`normative` 规范／`evidence` 证据／`runtime` 运行／`build` 构建 | 变更是否需 ADR？是否入库？可否丢弃？ |
| **角色** | `source` 原始物／`derived` 派生／`record` 记录／`decision` 决策／`tool` 工具／`asset` 资产 | 它是输入、输出、凭证，还是执行者？ |
| **命名域** | `slug`／`pinyin`（冻结）／`fixed`／`numbered`／`dated` | 新增文件该叫什么？ |

映射到 IEEE 828 的库分层：`product`＋`evidence` 的冻结部分＝受控基线（`en/`、`baseline/`）；`product` 工作件＝受控工作产品（`yuanwen/`、`a–z/`、`tasks/`）；`runtime`＝开发库（`script/`、`state/`）；`build`＝发布库。

### 5.2 七问容器契约（每个目录必须能答）

职责｜写入者｜命名域｜生命周期｜保留与处置｜判官（门禁）｜索引（README 或生成物）

前五问对应 15289 五属性，后两问是本仓库缺口所在。**答不全的目录，不得新增子项**——这一条把"未定义"从描述变成准入条件。

## 六、方案（按收益／成本排序）

### P0 单一源（零迁移，收益最高）

1. 新建 `rules/layout.json`：65 条根级条目 ＋ 二级容器声明，字段即七问 ＋ 域／角色／命名域。
2. `check_junk.py` 改为从 `layout.json` 生成 `ROOT_ALLOW`，删除硬编码字典。**双轨变单轨**。
3. `rules/01` 目录职责表改为由 `layout.json` 渲染或校验（门禁比对文字），不再手写。
4. 新增 `check_layout.py`，四项谓词：
   - `L1` 根目录实际集合 ⊆ `layout.json` 声明（新增条目未登记即红）
   - `L2` `rules/01` 表 ≡ `layout.json`（文字与条目双向一致）
   - `L3` 每个二级容器有 README／index，或列入豁免（`<letter>/`、忽略区）
   - `L4` `specs/<NNN>/` 符合 §6.2 schema（允许清单外子项即红）
5. 判据：`check_layout.py` 退出码 0；`L1` 预期命中 0（现无缺口），`L2` 预期命中 18（现存差集，首次运行即暴露），`L3` 预期 9，`L4` 预期 3（`tmp/`、`029`、`001` 散件）。
6. 成本：`layout.json` 约 70 条 × 7 字段，一次性撰写；脚本约 200 行（仅标准库）。
7. 回退：`git revert` 单次提交；`GATES` 删行即撤，CI 矩阵自动跟随（ADR-0061）。

### P1 容器补课（局部，低成本）

8. 生成 `specs/README.md`：41 行索引（编号／标题／状态／关键产物／执行记录形态），由脚本从 `spec.md` 首部与目录清单生成，禁止手改。
9. 统一 `specs/<NNN>/` schema，允许清单：`spec.md`（必需）、`plan.md`、`tasks.md`、`checklist.md`、`contracts/`、`execution-log.md`｜`execution-log/`（**二选一，禁并存**）、`bin/`、`results/`、`README.md`。禁止：`tmp/`、一次性脚本、规格根散落 JSON。
10. 迁移三件：`specs/script/tmp/` 删除（空目录）；`specs/029` 补 `spec.md` 或将 `report.md` 移入 `results/`；`specs/001` 的 9 个 JSON 迁 `results/`（同时改 `rules/01` 与 `cli.md` 中的路径引用，一处不漏）。
11. 判据：`L4` 命中 0；`specs/` 下无 `tmp/`；每个目录 `spec.md` 或 `results/report.md` 至少存一。

### P2 命名归一（中成本）

12. **冻结拼音目录**：`qian-yan/`、`guan-yu/`、`jian-yi-shu/`、`fang-fa-lun/` 只减不增；新增一律英文 slug。理由：拼音命名源于早期体例，已成路径契约，迁移破坏 `SUMMARY.md` 与站点链接，收益低于成本。
13. 顶层叙事文档在 `layout.json` 声明为 `normative`／`decision` 类，并注明 GitHub 识别顺序（根优先于 `.github/`），避免后来者"按 GitHub 惯例"搬进 `.github/` 造成双份。

### P3 物理分域（高成本，建议不做）

14. 若追求"物理上按域分目录"，需同时重建：`SUMMARY.md` 全部路径、`mu-lu-s.md` 链接、`assets/` 相对引用（`../assets/<slug>/`）、`.vitepress/config.mts` 的 `srcExclude`、七个 CI 工作流的 globs、`tools/` 内全部硬编码路径、`baseline/entries.json` 的 `zh_doc` 字段。
15. 评估：改动面覆盖 1,872 词条与 41 规格，收益仅为"目录名更整齐"，**不满足 rules/08 §5 不可逆决策的代价门槛**。建议长期停留在"逻辑分域"（`layout.json` 声明域），物理布局不动。

## 七、明确不做的事

* **不按文件类型重排**（把所有 `.md` 收进 `docs/`）。这会同时破坏 GitBook 空间、VitePress 路由、图片相对基座与 `SUMMARY` 单一事实源。
* **不动词条层**（`a–z/`、`1/`、`assets/`、`en/`、`yuanwen/`）。该层已由 `check_summary`、`check_images`、`divergence`、`check_yuanwen_fidelity` 四道门禁锁死，是全书最稳固的部分。
* **不为"整洁"引入新工具链**（YAML 解析器、目录生成框架）。JSON ＋ 标准库足够；引入依赖会与"tools 仅标准库"的既有约束冲突。

## 八、改判表（何种情况下推翻本建议）

| 触发条件 | 改判 |
| --- | --- |
| `specs/` 规模降到 10 个以下 | 放弃 schema 与索引，改用单文件规格 |
| 近期确定迁移站点构建或内容布局 | 先迁移，后规范；否则规范产物立即作废 |
| ISO 15489-1 修订版（目标 2029）改变分类要求 | §四、§五重审，`layout.json` 的域划分重定 |
| `en/` 解冻或改为外部存储 | `evidence` 域重划，`layout.json` 与 `check_junk` 同步改 |
| 出现第二套并行清单（如新的白名单脚本） | 先合并为单源，再谈其他；双轨是 D1 复发 |

## 九、风险

* **`layout.json` 与规则正文再次分叉**：由 `L2` 门禁比对消除；若比对本身失效，则风险回到 D1。
* **一次补 41 份 README 的边际价值递减**：建议只要求"一行目的 ＋ 关键产物"，由脚本生成骨架，不写长文。
* **标准引用过期**：ISO 15489-1 已在修订轨道，GB/T 26163.1 修订在批。本书所有标准条目均标核验日期，引用条款号前须回原文确认。

## 十、结论

用户"结构不清晰、大量未定义"的判断成立，但病灶定位需要修正：**根目录的存在性定义是完整的（缺口 0），缺的是职责定义（18 项）与二级容器 schema（`specs/` 41 个目录、8 种子目录名、0 份索引）**。

最优路径不是重排目录，而是**先立单一源、再补容器契约、最后（可选）才动物理布局**。P0 与 P1 合计约一次脚本开发加一次数据撰写，即可把"未定义"从描述性抱怨变成可判定谓词；P3 的成本是 P0＋P1 的一个数量级以上，收益却只是观感。

规范面没有"仓库布局国标"，但有四份可直接借用的：ISO 15489-1／GB/T 26162（分类与保留）、IEEE 828（配置项与基线）、ISO/IEC/IEEE 42010（关注点分离）、DA/T 22（件的整理）。开源侧以 Diátaxis（按需求分类而非按类型）与 REUSE（文件级声明完整性）最具迁移价值。
