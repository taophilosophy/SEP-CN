# 一次大重置：全局最优解建议书

**日期**：2026-11-17｜**性质**：评估＋方案（不实施）｜**授权范围**：允许废弃、合并、重组、重置既有翻译、状态、任务书
**体检产物**：`specs/042-progress-model-v2/bin/reset_audit.py`（只读判官）→ `results/reset-audit.json`
**前置**：`specs/042-progress-model-v2/spec.md` v3（C1–C29）、`specs/041`（A1–A14）、`rules/04`、`rules/06`

## 方向声明

* **意图复述**：用户授权不计成本，允许对既有译文、任务状态、任务书做废弃／合并／重组／重置，要求给出全局最优解。
* **目标**：用一次不可逆的投入，换掉“判据每变一次就要搬一次全库状态”的结构；重置之后，改善判据的成本与库规模脱钩。
* **判据**：①当前读数与事实的偏差归零；②判据变更的状态搬迁量为 0；③历史不可考的条目被显式标记而非隐去；④任一环节可单独回滚。
* **反目标**：不以“目录整齐”“命名统一”为目标；不动 `en/`、`yuanwen/` 的字节事实；不重译任何已过判据的译文。

## 一、体检：三个数字，两种读数

`reset_audit.py` 实跑结果（2026-11-17）：

| 面 | `state` 读数 | 历史事件读数 | 偏差 |
|---|---|---|---|
| 走完全链（含 R1–R3） | **1** | **385** | 385 倍 |
| 在途 | 411（s2.4_termchecked） | 其中 **366** 已走完全链 | 89% 被误读 |
| 有历史 | 582（含 steps） | **431**（含真实阶段节点） | 151 条只剩返工记录 |

三张分布并列，矛盾一目了然：

```
当前 state：pending 617 | s2.4_termchecked 411 | cleared 166 | s2.5_checked 3 | done 1 | checked 1
历史最高：  done 385 | s3 24 | r2 16 | r1 3 | r3 2 | s0 1 | 无记录 768
曾达 done 者：s2.4_termchecked 366 | cleared 16 | s2.5_checked 3
```

**结论一**：库里最接近“完成”的不是 1 件，是 385 件（含三审）。它们中的 366 件因为一次体例口径变更被回退到 `s2.4`，停在那里。

**结论二**：768 条任务（64%）没有任何阶段记录。其中 617 是 `pending`（从未开始，正常），149 是 `cleared`（被置空），2 条是 `done`／`checked` 却无历史。这 151 条属于**历史不可考**，不是“干净”。

**结论三**：`done` 事件在日志里出现 **408 次**，当前 `state=done` 只有 **1** 个。也就是说，交付这件事发生过 408 次，被记录了 408 次，但读数只承认 1 次。

## 二、成本结构：判据演进税

828 次 `revert-state`，归因只有三条：

| 归因 | 次数 | 出处 |
|---|---|---|
| 中文体例归一全量回退 | 411 | ADR-0063 / specs/039 P8 |
| 全量 done 回炉 | 219 | ADR-0053 |
| 全量回退（三轴硬门上线） | 198 | ADR-0043 |

**828 = 3 次口径变更 × 平均 276 条。** 这不是偶发故障，是稳定的单价：**每改一次判据，付 276 条状态搬迁。**

按过去三个月的频率（3 次），一年约 12 次，折合 3,300 条搬迁；每条搬迁要生成 evidence、核对 ledger、可能触发下游重跑。这是全项目最大的一笔结构性开支，且它**不产生任何译文**。

更严重的是副作用：搬迁把 `state` 挪回去，却把“曾经通过”留在 `steps` 里，于是读数与事实永久分叉。**分叉本身无法修复——只能整个换一种记账法。**

这笔税不是“多花了时间”，是“每改一次判据，就更难知道自己做到哪了”。继续在游标模型上打补丁，补丁本身会累积成新的解释负担（现有 68 条 ADR 中，至少 8 条在处理回退语义）。

## 三、最优解：J 体系（日志为事实，状态为视图）

### 3.1 四件套

| # | 载体 | 路径 | 只做什么 | 谁写 |
|---|---|---|---|---|
| 1 | **事件日志** | `journal/<letter>/<slug>.ndjson` | 记录发生过什么 | 唯一写入者 `journal_ops.py` |
| 2 | **判据登记表** | `rules/pipeline.json` | 声明每个节点的判据与降级策略 | 治理会话（ADR） |
| 3 | **派生视图** | `tools/progress.py` | 现算完成度、饱和、过期、分支 | 不写任何文件 |
| 4 | **分支返工** | 日志内的 `attempt` 字段 | 隔离返工，不改写历史 | `journal_ops.py rework/merge` |

判定权分离（A11 的延伸）：**1 是唯一写者，2 是唯一判据源，3 只读，4 只追加。**

### 3.2 事件只有六类，封闭

现有 42 种 `step` 名，其中 11 种是阶段、31 种是临时动作（`qa-rework` 33 次、`rework-open` 15 次、`post_done_fix` 3 次、`tail-normalize` 2 次……）。临时动作没有模型，所以每次都要新造一个名字。

收敛为六类：

| 类型 | 含义 | 关键字段 |
|---|---|---|
| `lock` | 源钉变更 | `sha256`、`pubinfo_date`、`edition` |
| `pass` | 某节点判据通过 | `node`、`attempt`、`gate[]`、`witness` |
| `fail` | 某节点判据失败 | `node`、`attempt`、`gate[]`、`reason` |
| `rework` | 开分支 | `attempt`、`from_node`、`reason`、`scope[]` |
| `merge` | 分支合回 | `attempt`、`into`、`verdict`、`arbiter` |
| `import` | 合成快照（迁移用） | `synthetic: true`、`basis[]` |

节点名从 `pipeline.json` 取，不写在事件里做自由文本。**新增环节＝改 `pipeline.json` 一行，事件类型不变。**

### 3.3 三段与节点（主干线性不变）

```
Seg1 英语提取   P1 lock → P2 convert → P3 reverse-verify → F1
Seg2 中文翻译   P4 preprocess → draft → s1 → s2 → F2
Seg3 审阅校对   s2.4 → s2.5 → s3 → R1 → R2 → R3 → F3
```

* 段固定（增段须 ADR）；**节点任意相邻位置可插**（承 v3 的修正）；
* 类型四选一只决定“判据写在哪”：`pipe`（ADR）、`stage`（该三位一体）、`review`（可增不可减）、`format`（段末闭合）；
* **R1–R3 是最小集**：任何 `attempt` 合回前必须全过，不可跳过、不可由分支内自审替代。

### 3.4 判据变更不再回退，只重算

这是全案的核心替换。旧做法：判据变 → 逐条 `revert-state` → 重走。新做法按新旧判据的包含关系分三档：

| 档 | 关系 | 视图动作 | 状态搬迁 |
|---|---|---|---|
| **放宽** | 新判据 ⊂ 旧判据 | 既有 `pass` 仍然有效，无需任何事件 | **0** |
| **收紧** | 新判据 ⊃ 旧判据 | 对既存 `pass` 重跑一次新判据：过则追加 `pass`（同一节点、更高 `gate` 版本），不过则 `fail` | **0**（只追加） |
| **更换** | 两者互不包含 | 开 `attempt` 分支，范围＝受影响条目；合回须 R 链全过 | 只涉及受影响条目 |

`revert-state` 从此不存在。它退化为 `rework --from <node>` 的同义词，且**目标态由 `pipeline.json` 的 `prev` 推导，不再硬编码两个值**（现行 `--to {s2.5_checked, s2.4_termchecked}` 的局限由此消失）。

### 3.5 J 公理（30 条，七组）

| 组 | 条目 |
|---|---|
| I 真相 | J1 钉一致、J2 源唯一裁决、J3 锁后不改（`en/` 字节） |
| II 记录 | J4 **日志只追加**、J5 **视图禁回写**、J6 **合成必标**、J7 事件六类封闭 |
| III 结构 | J8 三段固定、J9 节点任意可插、J10 类型定判据、J11 **R 最小集强制**、J12 段间契约、J13 格式段内闭合 |
| IV 前置链 | J14 单钉输入、J15 转换可重放、J16 双向保真、J17 差异二分（格式/实质）、J18 格式不外溢、J19 实质不落 md |
| V 返工 | J20 **返工即分支**、J21 分支隔离、J22 合并单向、J23 分支最小化、J24 冲突人工裁定 |
| VI 并发 | J25 写单元 `(entry, node)`、J26 认领互斥、J27 租约到期释放 |
| VII 机器 | J28 判官只读、J29 显式失败、J30 写后读回等值 |

与既有体系的关系：J1–J3 承 A1–A2；J4–J6 由 B4／B5／C5 强化为“日志而非状态”；J8–J13 承 C7–C12；J14–J19 承 C12–C17；J20–J24 承 C18–C22；J25–J27 承 C19–C20 并细化到节点级；J28–J30 承 A11–A14。**不是第四套公理，是 A／C 的合并终稿。**

## 四、大重置：W0–W6

一次性投入，七波，每波有独立判据与回滚点。

| 波 | 做什么 | 判据 | 回滚 |
|---|---|---|---|
| **W0** | 打 tag `pre-reset-20261117`；冻结 `tasks/` 写入 | tag 存在、`git status` 干净 | 无需 |
| **W1** | 派生日志：`steps` → 事件；无史者合成 `import{synthetic:true}`；`state` 转为最后一次 `pass` 的快照事件 | 事件总数 ≥ 4,993；385 件 `done` 事件全部在位；768 条 `synthetic` 全部标记 | 删 `journal/` |
| **W2** | 落 `rules/pipeline.json`：三段 16 节点、四类型、判据命令、`replay_on_change` 分档 | `check_stages` 四谓词全绿；节点引用闭合 | 删文件 |
| **W3** | 双写期：`task_ops` 同时写 `journal` 与 `state`，只读比对 | 连续 3 批（≥100 条）双写一致率 100% | 关双写开关 |
| **W4** | 切读面：`progress.py` 成为唯一读面；`PROGRESS.md` 改由它生成 | 新旧读数差异逐条可解释（差异清单为空或全部标注） | 切回旧读面 |
| **W5** | 删 `ORDER`／`STEPS`／`expected_prev`／`revert-state` 硬编码；`update` 死序列一并删 | 单测全绿；无工具引用旧符号 | revert 单提交 |
| **W6** | 公理合并：`specs/041` 转历史存根（保留文件、标注被 J 取代）；`specs/042` 升为唯一公理源；41 个 specs 按段归位 | `specs/README.md` 重生成；`check_layout` L1–L4 归零 | 恢复 041 状态 |

**W1 是唯一不可逆的一步**（它改变事实的存储形态），其余六波都可回滚。W1 的正确性靠“事件数单调不减 + 385 件 done 在位 + 768 条 synthetic 标记”三条硬判据兜住。

### 4.1 重置不等于重译

必须明确边界，否则“重置”会变成灾难：

| 对象 | 处置 | 依据 |
|---|---|---|
| `en/`（5,414 件）、`yuanwen/`（4,260 件） | **不动**，字节事实 | J3 |
| 已过 R 链的译文正文（366 件） | **不重译**，只按新口径复判 | 放宽/收紧档均为 0 搬迁 |
| `version_pin.sha256` | **保留**，转 `lock` 事件 | J1 |
| `tasks/*.json` 的 `state` | **删除字段**，改由视图计算 | J5 |
| `tasks/*.json` 的 `steps` | **迁移后只读留档**，不再追加 | 历史留痕 |
| `ledger.json`、`manifests/` | 保留，作为认领与批次事实 | J26 |
| `revert-state` 的 828 条记录 | **全部保留为事件**，它们是真历史 | J4 |

### 4.2 立刻兑现的三项

重置不是“先付代价后收益”，W1 完成当天就能拿到：

1. **完成度从 1 变 385**：`progress.py` 报“曾走完全链 385、当前口径下饱和 N”，N 取决于复判结果，但 385 是下界。
2. **366 件不必重译**：它们停在 `s2.4` 是因为被回退，不是因为没做完。复判只跑 `s2.4` 之后的三道判据，不重跑 `draft`–`s2`。
3. **判据变更单价归零**：从 276 条/次降到 0 条/次（放宽与收紧两档均只追加事件）。

## 六、重置后的读数（预期形态）

```
条目总数            1,199
─────────────────────────────
曾走完全链（含R链）    385   ← 今日已存在的事实，只是读不出来
当前口径下饱和         N    ← W4 复判后确定，N ≤ 385

已置空               166
```

不再有布尔“done”。`saturate(e)` 是集合包含判定：`passed(e) ⊇ nodes ∪ R`，而 `nodes` 可随 `pipeline.json` 扩展——**它在数学上随时可能由真变假，这就是“永不毕业”的形式表达。**

## 七、否决项

四条更“彻底”的路线，明确不做：

| 否决 | 理由 |
|---|---|
| 重译全部 1,199 条 | 366 件已过 R 链，重译是纯损失；重置对象是记账法，不是译文 |

## 九、结论

**这个库不缺译文，缺的是一本能回答“做到哪了”的账。**

385 件走完全链的成品在库里躺着，账上只记 1 件；828 次回退全部来自 3 次口径改进，每次改进都让账更难读。这不是执行问题，是记账介质的问题：**用一个会覆盖的字段，去记录一段不该被覆盖的历史。**

最优解因此不是“把状态重置成 pending 再跑一遍”——那是把 276 条/次的税再交一遍。而是**换介质**：日志记事实，视图算进度，判据变更只重算不搬迁。代价一次性付清（W0–W6），之后每次改判据的成本与库规模无关。

重置的边界同样明确：`en/`、`yuanwen/`、已过 R 链的译文，一个字都不动。**要重置的只有账本。**
