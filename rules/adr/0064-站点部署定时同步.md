# 0064. 站点部署定时同步（每 30 分钟自动拉子模块并部署）

**日期** 2026-11-16 ｜ **状态** accepted ｜ **权威** 用户指令“改成每30分钟自动同步？原来不是？”

## 背景与事实核对

* 用户提问附带一个事实判断：“原来不是？”——**核对结论：此前从未定时**。`git log --all -S "schedule:" -- .github/workflows/` 在壳仓零命中；四片并行时代的 `sync_deploy.yml`（3bd46c0 起）与 `push_deploy.yml` 触发只有 `workflow_dispatch`。旧工作流名“🔗 无电子书-**自动拉取**-部署”里的“自动”指**自动拉子模块到上游最新**，不是定时。
* 后果：站点发布完全依赖人工 `gh workflow run`，SEP-CN 前进后线上会长期滞后（本次核对时线上落后数个提交）。

## 裁定

1. 壳仓 `deploy.yml` 增定时同步，间隔 30 分钟（UTC），**错开整点**：实际写作 `cron: "7,37 * * * *"`——`:00/:30` 是 GitHub 定时扫描最拥挤的时刻，首次实测 11:30 那一拍延迟 20 分钟仍未触发。
2. 定时运行一律走**同步档**：`sync` 作业条件改为 `inputs.sync_docs || github.event_name == 'schedule'`——先 `git submodule update --remote` 拉 `docs` 到 SEP-CN 最新，指针有变则由 bot 提交指针并 push。
3. **指针未变不构建**：既有 `build.if` 已是“sync 跳过 或（sync 成功且 changed）” ，定时档无变更时整条链只跑一个检出作业（实测约 40 秒）后结束，不浪费分片构建。
4. 手动两档保留：`-F sync_docs=true`（同步＋部署）／`-F sync_docs=false`（只部署当前指针）。布尔输入必须 `-F`（`-f` 传字符串 `"false"`，在 `if` 里为真，会误触发同步档）。

## 成本与已知限制

* 每天 48 次触发；无变更时 48×约 40 秒检出，有变更时一次 6–7 分钟四片构建。
* GitHub cron 是**尽力而为**，且本账户实测延迟远大于文档口径：周/月级定时的实际触发滞后 **2.6–7.2 小时**（SEP-CN `sep-sync-check` 周一 18:30 → 实跑 01:43/01:09，滞后 6h39m/7h13m；`links` 月度 18:00 → 实跑 20:39/20:44/22:17，滞后 2h39m–4h18m，2026-09/10/11 三期）。30 分钟级的兜底高峰期可能滞后数小时甚至丢拍——**兜底不能当主路径**，准实时部署靠 C（推送即部署）。
* 2026-11-16 对照实验：壳仓 `7,37` 定时上线后 4 拍（12:07/12:37/13:07/13:37）全未出现，另推 5 分钟探针 `cron-probe.yml` 监控至触发为止；触发即证 schedule 已注册、属积压延迟，届时删除探针。
* 仓库连续 **60 天无活动**（无 commit/PR）会被 GitHub 自动停用定时任务，需在 Actions 页面重新启用。
* `concurrency: group: pages, cancel-in-progress: false` 保证与手动部署串行，不会叠跑。
* bot 提交的指针提交是生成物提交，不受 ADR-0059“人工提交即推”约束（推送本身由 workflow 完成）。

## 补充裁定（同日，用户批准“A＋C 并存”）

5. 壳仓 `deploy.yml` 增 `on.push.paths: [docs]`：**指针一提交就部署**（事件驱动，零空转）。bot 用 `GITHUB_TOKEN` 提交的指针不会再触发 push 事件（GitHub 的规则：由 GITHUB_TOKEN 产生的 push 不触发工作流），因此 sync 档不会自己触发自己。
6. 本仓新增 `tools/deploy_bump.py`：把壳仓 `docs` 指针前移到 SEP-CN 的 `origin/main`（可 `--ref`）、提交并推送，即“推完 SEP-CN 顺手续期”。要点：
   * 用 `git update-index --cacheinfo 160000,<sha>,docs` 写索引，**不用 `git add docs`**——后者记录的是工作树里子模块当前 HEAD，本地领先时会把未推送的提交写进指针，壳仓 CI 取不到该对象直接红；
   * 目标提交必须在 `origin/main` 上（`merge-base --is-ancestor`），否则拒绝（`--force` 才放行）；
   * 壳仓只允许动 `docs`：其它未提交改动默认拒绝（`--allow-dirty` 放行），落后于 origin 时先 `merge --ff-only`，有本地未推送提交则拒绝而非自动 rebase（不与并行会话抢）；
   * `--gate` 先跑 `check_all.py`，非全绿不前移；`--dry-run` 只报告。
   * **区间内没有站点改动就跳过前移**：指针 `cur` 到目标之间若只动了 `en/`、`specs/`、`tools/`、`tasks/`、`state/`、`script/`、`rules/`、`.github/` 等不参与构建的路径（照抄 `.vitepress/config.mts` 的 `siteExclude`，另加 `yuanwen/SUMMARY*.md`），不为它重建整站，直接返回；下次真有站点改动时一并带过去。`--always` 可强制前移。两处刻意偏离：`baseline/` 虽不产页面但 `entries.json` 在构建期定版本钉与 `enPath`，**算站点改动**；`yuanwen/` 词条页照常参与构建（只排除它的两份 TOC 镜像）。
   * 单测 7 例（`tools/tests/test_deploy_bump.py`）：临时双仓（bare origin + gitlink）验证前移、幂等、dry-run、脏区拒绝、未推送目标拒绝、无站点改动跳过（后续站点改动再一并前移）、`baseline/` 算站点改动。
7. 定时轮询（`cron: "7,37 * * * *"`）保留为**兜底**：覆盖未走脚本的推送（他人/他机会话直接 push、bot 提交、钩子失手）。

## 回退

删 `on.schedule`（兜底轮询）与 `on.push`（事件触发）两段即可回到纯手动；`sync` 条件中的 `github.event_name == 'schedule'` 随之失效但无害。
