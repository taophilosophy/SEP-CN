# 0092. 文档形态三分与规则作用域派生

**状态**：accepted | **日期**：2026-11-28

## 背景

064 审计的 G6 指出：规格容器“三件套”只有习惯，没有成文判据——“工具型”不是充分分类，需显式文档类型或风险等级；G8 指出：规则作用域若逐条写进规则头，会制造重复元数据，且与 `rules/pipeline.json` 的 `criteria_owner`／`criteria_carrier` 形成第二本账。

11 件 E2E（T130–T162／T185–T271）与 T166 测试补齐后，两个缺口的处置成本与边界已可判定：形态判据可由目录与文件存在性机检；作用域可由现有登记册派生，无须新增手写字段。

## 决策

1. **文档形态三分**（G6）：
   * **单页卡**：仅 `spec.md`；用于一句话可收口、无多阶段执行的任务（允许 `plan.md` 单存，视为规划卡）。
   * **标准三件**：`spec.md`＋`plan.md`＋`tasks.md`；凡出现 `tasks.md` 即须有 `plan.md`，否则判 `triple-incomplete`。
   * **登记／规则**：`rules/`、`baseline/`、登记册等不适用 spec 三件套，不建 `specs/` 空壳。
2. **规则作用域派生**（G8）：
   * 唯一派生源为 `rules/pipeline.json` 的 `criteria_owner`（判据→节点）与 `criteria_carrier`（例外承载体）。
   * `rules/0X-*.md` 头部**不得**手写 `applies_to:`；作用域视图由登记册生成，不逐条维护。
   * 机检三条：节点判据须有 owner；owner 须有 `tools/<name>.py` 或 `criteria_carrier` 例外；owner 不得为无节点引用的孤儿（`note` 元数据除外）。
3. **机检落地**：`tools/check_doc_shape.py` 同时执行上述两组检查；正反例 `tools/tests/test_doc_shape.py` 11 例（单页卡、规划卡、三件套、tasks 缺 plan、缺 spec、手写作用域、owner 缺失、载体缺失、载体例外、孤儿 owner）。
4. **适用范围**：2026-11-28 起新建 `specs/NNN-*` 容器应过形态检查；存量容器不追溯拆分，发现即登记于本 ADR“后果”节，不静默改史。

## 替代方案

* **按“工具型／文档型”分类**：G6 已否证——“工具型”既非充分也非互斥，无法稳定判定。
* **每条规则头写 `applies_to`**：G8 已否证——与 pipeline 登记册重复，修订时双写漂移。
* **新建 `rules/rule-scope.json`**：现有 `pipeline.json` 已含 owner／carrier 与节点判据，新建即第二本账。
* **把检查器立即加入 `check_all`**：会改变 23 项门禁基数与 CI 行为，宜在 W6 流程 v2 收口时统一评估；当前先以独立命令与单测固化判据。

## 后果

* `rules/09-process-standard.md` §3.1 增“文档形态与规则作用域”条；§6 批次开工自检增 `check_doc_shape`。
* `rules/adr/README.md` 索引补 0092。
* 存量 `specs/005-translation-campaign` 为 `spec＋plan` 规划卡（无 tasks），按第 1 条允许；不补空 `tasks.md`。
* `tools/check_doc_shape.py` 已对全库跑通 0 issue；未入 CI，待 W6 评估。
* 回退：删除第 1 条即恢复习惯口径；删除第 2 条即恢复逐条作用域；检查器与测试可整体移除，不影响既有门禁。
