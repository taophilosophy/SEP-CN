# 0026. 双机双克隆工作区（本机迁入本地 C 盘）

accepted | 2026-11-09

## 背景

工作区实际位于 `//Desktop-m5p610n/d/SEP-CN`（SMB 共享，非本地盘），而另一台机 Desktop-m5p610n 的 `D:\SEP-CN` 就是同一克隆。实测代价：`git status` 495 ms、`git diff --stat` 1067 ms、`check_all.py` 27 s（本地基线 ~6 s）；仓库 7461 个跟踪文件、含本地相 2.1 GB，日常是海量小文件 I/O，SMB 每次 stat/open 都是一次网络往返。

同时该机将继续并行翻译其他词条，因此迁移不是「搬到一台机」而是**把共享克隆拆成两个独立克隆**，需要一套双写协议。

## 决策

1. **M1（DESKTOP-RLOEIG9）**：新建本地克隆 `C:\Users\ykla\Documents\SEP-CN`，日常操作全部在本地 NTFS 完成；此后**不再写 D:**（卸载映射或只读）。
2. **M2（Desktop-m5p610n）**：`D:\SEP-CN` 原克隆保留，继续处理其他词条，不做改动。
3. **唯一同步面 = `origin/main`**（GitHub private）。两机互不以对方工作树为真值。
4. **push 节奏 = 三个检查点**：批次认领（抢锁）／阶段推进（`campaign.py advance`）／条目 done 收口。其余微提交留本地——这是「仅必要的才 push」的可执行定义。
5. **不建长期分叉线**：不开 GitHub fork；需要隔离的实验才用 `exp/<name>` 短命分支，翻译批次直接提交 main。
6. **生成物冲突重生成**：`PROGRESS.md` 冲突任取一侧后 `tools/progress.py`；`SUMMARY.md` 取并集后 `check_summary.py`；登记册追加式书写、冲突取并集后 `check_terms.py`。
7. **本地相各机自持**：`en/`、`yuanwen/`、`script/`、`state/`、`.secrets/`、`node_modules/` 不入库、不共享；`en/`、`yuanwen/` 以 `baseline/` 与 `specs/001/en-integrity-full.json` 台账对齐。

## 后果

**正面**

* 基础操作与门禁回到本地盘量级；批量翻译、对账脚本的 I/O 成本大幅下降。
* 两机物理独立，SMB 抖动、单机负载不再互相拖累；D: 侧工作不被迁移打断。
* 迁移零改码（已确认 tools/specs/rules 无绝对路径引用）。

**负面 / 需跟进**

* 从此有**真实合并**：账本、`PROGRESS.md`、`SUMMARY.md`、登记册出现文本冲突。已用「认领锁 + 生成物重生成 + 追加式登记」压低概率，但需按 `specs/014` 的冲突表处置。
* push 频率不足时两机分叉面变大；作业单要求开工先 `pull --rebase`、认领即 push。
* 记忆按工作区路径键存放，新路径会开空记忆项目，必须人工搬运（`specs/014/cutover-runbook.md` §5）。
* 本地相 2.1 GB 每机一份，磁盘占用上升（C 盘余量 812 GB，可承受）。
