# 0059. 提交即推：解除「未经要求不 push」，改为每次提交后自动 push

accepted | 2026-11-16

## 背景

原口径分散在三处：`rules/05-ci-and-tools.md`「直接提交 main 分支；未经用户要求不 push、不做 force 操作」、`AGENTS.md` 硬约束表「提交纪律」同款、`rules/06-governance.md` 与 ADR-0026/0028 的「push 三检查点（认领／advance／done）＋积压线（途中 ≤1、收工清零）」。

实际运行的代价：

* 多会话共树、每日常态十余个提交，本地积压成为常态（2026-11-16 开工时领先 `origin/main` 6 条，含多会话成品提交），「收工清零」与「未经要求不 push」两条互相拉扯，收工只能上报积压；
* 积压直接放大 rebase/代推窗口——ADR-0028 的同步事故（M1 侧 4 个大提交被判弃、强制覆盖）诱因之一就是长积压；
* 远端因此长期不是最新真相面：CI、GitHub Pages、跨机（M1/M2）同步都落后于本地数个提交，排查时先要问「到底推没推」。

用户 2026-11-16 裁定：解除「未经要求不 push」，改为自动 push。

## 决策

1. **提交即推**：每次 `git commit` 成功后立即 `git push`（不带 force）。提交粒度不变（小步提交仍按 rules/05），推送粒度与提交粒度对齐。
2. **推送前必排他**：先 `git fetch`；落后即 `python tools/sync_guard.py pull`（fetch＋rebase＋判弃自检实拦，ADR-0028）；推送被拒（non-fast-forward）→ 重跑 pull 后再推。**`--force` 仍禁**（历史改写走 rules/06「历史改写与批次护栏」的备份 tag 前置，不属本 ADR 管辖）。
3. **积压线作废**：「途中 ≤1、收工清零」（ADR-0028 裁定④）不再作为独立约束——自动 push 使其常态化归零；收工核对改为 **`git log origin/main..main` 为空**（硬验收不变）。推不出去（代理不可用、网络中断）时记录失败命令与时间留痕，恢复后第一件事补推。
4. **门禁红不阻断推送**：存量红（术语表等）与并行会话在途改动会让本地门禁间歇报红，而「红了就不推」只把提交关在本地、放大 rebase 窗口。门禁职责不变（开工/收工跑门禁、推送后 CI 为最终裁判）；推送只负责让远端成为唯一同步面。
5. **并行会话代推属正常**：push 会连带推走同一克隆内其他会话已提交的提交；提交信息与归属不变，不再视为异常。ADR-0028 孤儿件处置（`git cherry` 判内容）仍适用。
6. **用户可临时叫停**：需要暂停推送时以当轮指令为准——自动 push 是默认行为，不是不可推翻的硬线。

## 后果

* **正面**：远端始终是最新真相面；积压与 rebase 竞态窗口显著缩小；跨机同步、CI 与 Pages 构建反馈及时；「推没推」不再需要事后核对。
* **代价**：提交即公开（GitHub 公开仓、Pages 构建触发），真半成品一旦提交会立刻外显。因此「小步提交」的前提是**每步可验收**，不得为凑推送而提交半成品；CI 失败要跟手修，不再有「本地攒着再看」的缓冲。
* **保留**：force push 禁令、备份 tag 护栏、判弃自检、只提交相关文件的 pathspec 纪律、提交信息中文一行。
* **规则面**：ADR-0028 裁定④（积压线）就推送积压部分作废，定岗分工与判弃自检条款继续有效；ADR-0026 的推送检查点降为「检查点必须推」的义务描述，语义由本 ADR 覆盖。
