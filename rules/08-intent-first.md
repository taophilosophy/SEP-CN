# 任务意图与方向先行（知难行易）

本规则落实宪法第 VII 条（知难行易：先明方向，后择手段），适用于**全部会话与全部任务类型**——翻译、校对、结构改动、术语登记、管线工具、站点、规则修订、发布。理论底稿见 `reference/engineering-doctrine/00b-zhinan-xingyi.md`；本文件是约束性条文，冲突时以本文件为准。

## 1. 开工前方向声明

任何任务在动笔、动代码、跑批之前，先用一句话复述**用户到底要什么**（意图，不含手段与自己偏好的方案），并写清：

| 字段 | 要求 |
| ---- | ---- |
| 意图复述 | 用户原话加一句话转述；不得替换成自己熟悉的问题 |
| 目标 / 非目标 | 要达成什么；明确不做什么 |
| 验收判据 | 可执行的二值判据（命令加期望输出、检查器、交付物形态） |
| 约束与代价 | 边界条件、由谁承担负面后果 |

落点：文档任务写入任务 JSON 的 `evidence`（首条）；工程改动写入 `specs/<NNN>-*/spec.md` 或 ADR 的“背景/决策”节；极简任务可在回复中一句话完成。写不出这句话，视为尚未立项。

## 2. 需求不明：先问不猜

* 指令存在两种以上合理解释、缺少验收判据、或与既有规则冲突时，先向用户确认（提问并给候选方案与影响），不得自行假设后直接实施。
* 确需临时推进时，假设必须显式标 `[假设]`，并把验证该假设作为第一步；假设被推翻即停手重定向。
* 禁止把“业界惯例”“工具默认”“上一个任务这么做”当作需求来源。

## 3. 手段后置且可替换

* 工具、框架、流程、脚本是实现变量，不是目标；选择手段须说明为何此手段服务于该目标、替代方案是什么、何时替换。
* 禁止以“已运行某工具”“已走完某流程”“文档已写”作为完成证据；完成证据只能是验收判据的通过结果与可复核凭证。
* 工具或流程与实际目标冲突时，改手段，不改目标；确需改目标，回到第 1 条重新声明。

## 4. 以验收判据验收

* 完成等于验收判据全部通过加证据可复核；不以提交数、文档长度、工时、在线状态衡量。
* 收工自检：本次工作改变了哪个决策、产物或门禁？答不出，视为形式主义，删除或降级（doctrine §9）。

## 5. 可逆快行，不可逆先知后行

* 可逆决策（草稿、试验分支、临时脚本、可回退的小改动）允许快速试错，试错结果必须留痕。
* 不可逆决策（结构重排、批量改写、数据格式、协议、权限、对外发布、破坏性动作）必须先方向声明并写清代价，再按 [06](06-governance.md) 的前置条件执行。

## 6. 知与行的闭环

方向声明不是拖延许可证。明确方向后立即执行**最小可验证步骤**，用结果修正理解；禁止以“还没想清楚”为由长期停滞，也禁止以“先做起来再说”绕过方向确认。

## 7. 判例

| 场景 | 错误做法 | 按本条做法 |
| ---- | ---- | ---- |
| 用户说“优化一下” | 直接改代码或改结构 | 先问：优化哪个指标、现状值、目标值、如何验证 |
| 用户说“新增某理论并全局落实” | 直接新建文件、只改一处规则 | 先确认理论主题、来源、落地层级（reference、rules、宪法）与验收形态 |
| 翻译任务起步 | 先跑脚本、先建目录 | 先确认词条范围（含补充材料）、六道验收与学术挂钩，再创建任务 |
| 用户指令与既有规则冲突 | 默默按自己理解执行 | 指出冲突，给两种方案与影响，请用户裁定 |
